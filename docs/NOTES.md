# applereplay: Apple TV (1st gen) Apple II retro-emulation box, engineering notes

Notes for whoever works on this next, human or Claude Code (CLAUDE.md loads this
file). Anything about one particular build host, TV or account belongs in
CLAUDE.local.md, which is gitignored.

## Goal
Original Apple TV (first generation, model A1218, 2007: 32-bit EFI, Intel ~1GHz, NVIDIA G72 / GeForce Go 7300; the only Apple TV this can run on, since every later one is an ARM machine, not a PC) boots Debian 12 (bookworm, i386, Debian kernel `linux-image-686-pae`, currently 6.1.0-56 = upstream 6.1.192, Debian 6.1.192-2) from a USB flash drive via `atv-linux-loader` (`boot.efi` -> fake `mach_kernel` containing kernel+initrd) straight into linapple running Total Replay.

## Making a change
- Work on a branch, not straight on main. To build and test in a second working tree (`git worktree`), it needs its own out/ (copy out/ssh and out/hostkeys from the first, or the box won't know your key), a copy of assets/, `git submodule update --init`, and env/root (a symlink to the first tree's works). Symlinking out/ or assets/ doesn't work: env/run only sees the tree it's in.
- Builds stay rootless. Root is only for writing the stick (`bmaptool`, `sgdisk`).
- Change the image through the repo (overlay/, hooks/customize.sh, build.sh, mkimage.sh, patches/), never only by hand on the box. A fix tried on the box isn't done until it's in the repo.
- linapple changes: edit out/src/linapple, `env/devroot build` + `install`, measure with `sudo fps`, then save the diff to patches/ before ./build.sh resets the source. Check patches with `-std=c++11`.
- Scripts are `/bin/sh`, indented 4 spaces (.editorconfig), and must pass shellcheck with no warnings (tests/static.sh). No formatter: shfmt was tried and wanted to change about 75 lines in any configuration, for no gain.
- Prefer Debian packages and Debian's kernel. No nouveau, no OpenGL, no mode changes (see Display rules).
- Nothing personal in tracked files: host names, home paths, IPs, email addresses and keys go in CLAUDE.local.md or out/ (tests/static.sh fails on this machine's host name and on names listed in out/private-names). Nothing from assets/ gets committed.
- Before committing: `tests/run` (plus `TEST_BOX=1 tests/run` if the box was involved), and a test in tests/ for new tooling. If the image changed: `./build.sh` (it must not report unresolved libraries) and `./mkimage.sh`, then check on the box (services, `journalctl -u`, `sudo fps` at 60) and at the TV for picture and sound.
- After rebuilding an image you will flash or publish: `env/vuln-check --record` and commit docs/image-packages.status, so the weekly check on GitHub (see Security) speaks for the current build.
- Keep these notes current: facts learned, gotchas, status; move finished items out of Next; fixes worth sending upstream go under Upstream contributions. Update README.md if its steps changed.

## Hardware and image facts
- Image layout from mkimage.sh: GPT, p1 = 511M FAT `BOOT` (PARTLABEL `boot`, type Apple TV recovery) with boot.efi, mach_kernel, com.apple.Boot.plist, BootLogo.png, System/Library/Extensions/Dummy.kext; p2 = 6G ext4 `debian-root` (PARTUUID b632a136-1138-4ea8-9ead-c8891c82dcac). The rest of the stick is unused for now.
- Boot partition GPT type must be "Apple TV recovery" `5265636f-7665-11aa-aa11-00306543ecac` (GParted's `atvrecv` flag); root is a normal Linux filesystem partition.
- Kernel Flags: `root=PARTUUID=b632a136-1138-4ea8-9ead-c8891c82dcac ro video=vesafb net.ifnames=0 consoleblank=0 init_on_alloc=0 modprobe.blacklist=nouveau quiet splash loglevel=3 systemd.show_status=false udev.log_level=3 rd.udev.log_level=3 vt.global_cursor_default=0` (everything from `quiet` on is for the boot splash; see Boot splash). The box can edit them itself: `sudo mount /boot/atv`, edit com.apple.Boot.plist, reboot.
- Decision: keep Debian's kernel; consider a self-built one only if needed. Debian names kernels by ABI (6.1.0-56) while the upstream version is 6.1.192; same kernel.
- Game controller: a wired Xbox 360 pad (tried: a Mad Catz one, USB 1bad:f016, which declares 500 mA) is handled by the kernel's xpad driver with nothing added to the image, and shows up as /dev/input/js0 and an event device (user apple is in group input). linapple reads it through SDL's joystick interface: `Joystick 0 = 1` in its config, stick axes 0 and 1 (the left stick), buttons 0 and 1 (A and B). The config is one mode per Apple II joystick, and with mode 1 and no controller linapple falls back to the mouse (4), not the keypad (2) the image uses; so xsession switches to mode 1 only when a /dev/input/js* exists as the emulator starts, and logs it to the journal as `joystick`. A controller plugged in later needs the emulator restarted (F12). Played and approved at the TV (2026-11-11), 60 fps with the pad active. The d-pad is a hat (ABS_HAT0X/Y), which upstream linapple doesn't read; patches/linapple-joystick-hat.patch makes a pressed direction override that axis with full travel (0 or 255), like a digital stick, leaving the analog stick in charge when the d-pad is at rest. Confirmed at the TV for up, down and right (2026-11-15). Left is unverified: the pad it was developed on never sends it (a five-minute `evtest` recording had 34 ABS_HAT0X events, all 1 or 0, never -1, across five deliberate presses of left; up, down and right all appeared), so that pad's left contact is dead and the patch's left branch, the mirror of right, has not been seen working. To check a pad: `evtest "$(readlink -f /dev/input/by-id/*-event-joystick)"` and press each direction (ABS_HAT0X -1/1 is left/right, ABS_HAT0Y -1/1 is up/down). Use the by-id name: event numbers change between boots (the pad was event10 on one boot and event6 on the next), and a recording of the wrong device shows nothing. Known limits: linapple applies no dead zone, and this pad's stick rests about 4-5% off centre (-1408, 1642 of 32768), which the games tried didn't mind; the keyboard is still needed for Total Replay's menu and for Ctrl+F10.
- USB: the Apple TV has one external port (USB 2.0), so the stick and the keyboard share a hub. The setup this was developed on: a powered USB 2.0 hub, a USB 3.0 stick (57.8 GB) and an Apple USB keyboard from a 2006 iMac; boot.efi boots from the stick through the hub. Checked 2026-11-11: the port is USB 2.0 (Apple's spec sheet lists "USB 2.0 (for service and diagnostics)"; on the box, `lspci` shows an ICH7 EHCI controller and `lsusb -t` has the hub and the stick at 480M; a second, UHCI controller carries only the built-in IR receiver). Why a powered hub: the USB 2.0 spec lets a bus-powered hub pass one unit load, 100 mA, to each port, and Linux won't configure a device that declares more than its hub's budget; this stick declares 300 mA (`bMaxPower`), the keyboard and its built-in hub 50 mA each. The hub here reports itself self-powered (`lsusb -v`: "Self Powered"), so each port gets 500 mA. An unpowered hub is untried; by those rules the stick would be refused, though devices and hubs often ignore them. Stick size: the image is 6,980,370,432 bytes (1 MiB + 511 MiB boot + `ROOT_SIZE_MIB` 6144 + 1 MiB), fixed by mkimage.sh and not by what's installed (about 1.3 GB of the root partition is used), so an 8 GB stick is the minimum; a 4 GB stick would need `ROOT_SIZE_MIB` of about 3000 or less, untested.
- Slow sticks (2026-11-15): a no-name USB 2.0 stick ("VendorCo ProductCode", 31.5 GB) wrote and read back correctly but booted in 2 min 58 s and again 2 min 59 s (kernel 15 s, userspace 2 min 44 s), against about 30 s on the USB 3.0 stick. No USB errors or resets, link at 480M; /proc/diskstats showed writes averaging 569 and 683 ms and reads 37 ms over each boot (a dd test right after got 6 ms per flushed 4 KB write, so it is fast only when idle). Everything waiting on the disk came out slow (dev-sdb2.device, systemd-udevd, ifupdown-pre, ssh), and systemd-machine-id-commit failed both times, killed at its 90 s timeout, so the machine id stayed transient. Read speed through the box was 10 MB/s. To judge a stick: `systemd-analyze` and `systemd-analyze blame` after boot, and the write and read times from /proc/diskstats (fields 8/11 and 4/7).
- The Apple TV's internal hard disk is left untouched: the image never mounts or writes it, so Apple's software stays as it was and the box is an Apple TV again without the stick. On the box it is the 149 GB ATA disk with Apple's partitions EFI, Recovery, OSBoot and Media. Its name depends on which driver finds its disk first: it was sda with the stick as sdb, and since the initramfs carries only USB drivers (2026-11-17) the stick is sda and the internal disk sdb; so nothing should name either by sdX. Nothing on it is mounted: fstab names only the stick's partitions (`LABEL=debian-root`, `PARTLABEL=boot`, neither of which the internal disk has), the kernel's root is the stick's PARTUUID, udisks (desktop automounting) isn't installed, and systemd's GPT auto-generator mounts nothing here (it only acts on a disk a systemd-compatible boot loader names, which boot.efi isn't). tests/box.sh checks that every mounted disk partition is on the stick. Keep it that way: anything that would use the internal disk (swap, storage for saved games) changes what the README promises, so it would need saying there first. Booting Apple's software with the stick out, tried 2026-11-17/18 (filmed): the first time, a few seconds after unplugging, the TV showed the last shutdown screen for two frames (the graphics memory had kept it through the short power cut; not seen after a longer one), then Apple's logo, a restart, and Apple TV Recovery (a language list, then Restart / Run Diagnostics / Factory Restore). Restart there started Apple's software normally. The second time, right after a boot from the stick, Apple's software started directly: logo about 4.6 s after the signal, its menu at about 36 s. So booting the stick doesn't send the box to Recovery; why it went there once is unknown (Apple's software hadn't run for a long time before that).
- The Apple TV's IR receiver (Apple Inc.) shows up as a USB device. Wired Ethernet with DHCP; the box announces itself as applereplay.local (avahi).
- Naming: **applereplay** is the project and the Apple TV (hostname `applereplay`, /etc/hosts `127.0.1.1 applereplay`). Things about the Total Replay software keep `totalreplay` names on purpose: totalreplay-kiosk, /etc/totalreplay, /usr/local/lib/totalreplay, out/ssh/totalreplay_ed25519, out/totalreplay.img. mmdebstrap/debootstrap copy the build host's /etc/hostname into the rootfs; always write it in a customize hook (the overlay does).

## Build host
- Any x86_64 Linux with mmdebstrap, bubblewrap and unprivileged user namespaces. Builds are rootless: mmdebstrap `--mode=unshare` (needs a subuid/subgid range).
- If the project lives in a home directory that other users can't enter (mode 750 is common), mmdebstrap's namespace root can't read project files directly. So build.sh copies the keyring to a world-readable temp dir, and gets project files into the rootfs with mmdebstrap's `sync-in`/`upload` special hooks, not `cp` from a shell hook.
- Ubuntu/Mint lack Debian's archive keys: `env/keyring/*.asc` comes from Debian's debian-archive-keyring 2025.1.
- `env/bootstrap.sh` builds the toolchain (Debian trixie amd64) into `env/root`; `env/run <cmd>` runs a command in it via bwrap with the project at /work (you appear as root inside; files stay owned by you). Has clang 19, xxd, autotools, kernel build deps, gdisk, mtools, dosfstools, e2fsprogs 1.47.2 (`mke2fs -d` accepts a tarball), shellcheck 0.10.0 and python3-apt for env/vuln-check (both added later: in an older env/root, `env/run apt-get -o APT::Sandbox::User=root install shellcheck python3-apt`). Packages whose install scripts chown to another user (debsecan) can't be configured inside env/run, which has only one user id. It has no SDL2 headers; linapple is built with env/devroot instead (see Performance).
- `env/build-cctools.sh` builds cctools-port into /opt/cross inside env (needed to link mach_kernel). It is pinned to commit 9fc3e04 (the head of branch `986-ld64-711` on 2026-11-11) so the linker can't change unnoticed. Rebuilding ld from the pin gave a different ld binary than the one built earlier from the branch, but a byte-identical mach_kernel.

## Boot loader
- `mach_kernel` comes from github.com/DistroHopper39B/atv-linux-loader (submodule src/atv-linux-loader, pinned at d0b1076): `make KERNEL=vmlinuz INITRAMFS=initrd` with clang + `/opt/cross/bin/i386-apple-darwin8-ld`. It embeds kernel+initrd, so any kernel change means rebuilding mach_kernel.
- Boot logo: boot.efi draws the image that com.apple.Boot.plist's `Boot Logo` key names (a file on the boot partition), centred on `Background Color`; without the key it draws a grey Apple logo. Ours is logo/BootLogo.png, drawn by logo/make-logo.py (pure Python 3, no libraries): pixel art on a 160x90 grid in Apple II hi-res colours, written at 4x as a 640x360 8-bit RGB PNG with no alpha and no interlacing. That is the only size and flavour tried, and boot.efi showed it correctly on the first attempt (judged at the TV, 2026-11-11). Its small print says "2007 hardware", the year the Apple TV went on sale (Apple first showed it as "iTV" in September 2006, which is why it said 2006 until 2026-11-18). It is original art on purpose: no Apple logo and nothing from Total Replay or any game, because the repo is meant to be public. To change it: edit make-logo.py, `logo/make-logo.py > logo/BootLogo.png` (tests/static.sh checks the two agree), try it on the box (`sudo mount /boot/atv`, copy it over /boot/atv/BootLogo.png, reboot, look at the TV), then ./mkimage.sh.
- Boot splash (Plymouth, Debian 12's 22.02): instead of boot messages, the boot logo (the same BootLogo.png, centred) with a bar of 32 blocks in the Apple II hi-res colours under it, which Plymouth fills by its estimate from earlier boots (the first boot's estimate is poor; it learns), then the box's address under the bar for 3 s, then Total Replay. The theme is a Plymouth script (overlay/usr/share/plymouth/themes/applereplay/applereplay.script) with images from logo/make-splash.py (blocks, and digits, a dot, I and P for the address: the label plugin that draws text would bring pango and cairo); tests/static.sh checks the images match the script. It draws on the firmware's framebuffer through Plymouth's frame-buffer renderer; no DRM, so nothing here changes the display (see Display rules). Esc shows the boot messages; `journalctl -b` has them all. How it ends: plymouthd only takes commands from root, so applereplay-splash-end.service (root, no capabilities; `systemd-analyze security` 2.1) shows the address and runs `plymouth quit --retain-splash` just before the login on tty1, and getty@tty1 is told not to reset tty1 (TTYReset, TTYVHangup, TTYVTDisallocate off) so it stays in graphics mode with the splash's last picture and neither the login line nor X's banner appear; Plymouth's own quit services are masked. With /etc/totalreplay/no-kiosk it quits without retaining, so the shell shows. A second or two of black remains while X starts: X's fbdev driver clears the screen, and `-background none` doesn't help with fbdev. Gotchas: `DeviceTimeout=0` in plymouthd.conf (meant to skip the 8 s wait for a DRM device) makes plymouthd abort on an assertion in its timer code, and then there is no splash at all; it is 1, and tests/image.sh checks it's above 0. Plymouth's initramfs hook needs fc-cache (package fontconfig) and copies every DRM module and font into the initramfs; overlay/etc/initramfs-tools/hooks/zz-applereplay-trim removes them again. A serial console (`console=ttyS0`) makes Plymouth fall back to text, so don't judge the splash with one. At shutdown: the logo without the bar, then, once the filesystems are unmounted or read-only, "IT IS NOW SAFE TO TURN OFF YOUR COMPUTER." under it. The Apple TV can't switch itself off (after a poweroff its light blinks and the screen keeps the last picture for good), so without that line nothing says when to unplug. It comes from overlay/usr/lib/systemd/system-shutdown/applereplay-safe-to-turn-off, which systemd-shutdown runs as its last step; by then it has killed every process except those whose name starts with @, so drop-ins for plymouth-poweroff and plymouth-halt start plymouthd as `@plymouthd` (without them the hook finds no plymouthd and the message never shows). Seen on the Apple TV (2026-11-16, the boot part): the splash, the address under the bar and Total Replay after it; boot 24 s to the login on the USB 3.0 stick (35 s before, without the splash's quiet flags). The splash's logo is drawn pixel for pixel (640x360 on 1280x720) and looks larger on the TV than boot.efi's, so the hand-over shows as a jump in size; judged fine. The shutdown message was seen at the TV on 2026-11-17. That day's image (kernel 6.1.192-2) took 26.6 s to the login on its first boot and 24.8 s on the second (10.4 s kernel), with Total Replay on screen at 29.2 s. TEST_BOX=1 tests/run box passed: 60 fps median, 42% CPU idle, 66 of 233 MB in use, and Plymouth gone after the boot. Most of the difference between boots is DHCP (ifupdown-pre plus networking, 7.5-9.2 s).
- Trying boot changes in QEMU: env/run can run QEMU unpacked from Debian's packages (`apt-get download`-style into out/qemu; installing qemu-system-x86 in env fails on the passwd package, which env's single user id can't own). Boot `-kernel out/boot/vmlinuz -initrd out/boot/initrd` with the image as a USB stick on an EHCI controller, like the Apple TV's (`-drive file=out/totalreplay.img,format=raw,snapshot=on,if=none,id=stick -device usb-ehci,id=ehci -device usb-storage,bus=ehci.0,drive=stick`; an IDE disk no longer boots, since the initramfs has only USB drivers), the kernel flags from out/com.apple.Boot.plist plus `vga=0x344 module_blacklist=bochs,bochs_drm` (a 1024x768x32 VESA framebuffer like the Apple TV's efifb; with QEMU's bochs DRM driver Plymouth and X behave differently), `-nic user,model=rtl8139,hostfwd=tcp:127.0.0.1:2222-:22` for SSH with out/ssh's key, and `screendump` on the monitor socket for pictures. Without KVM in env/run it reaches Total Replay in about a minute. applereplay-fb-wc fails there (no efifb), which is expected.
- Where boot time goes (a phone video of a boot, 2026-11-17, the splash image on the USB 3.0 stick): power-on to boot.efi's logo about 7 s; boot.efi's logo for about 67 s while the firmware reads mach_kernel (30 MB then) from the stick, about 0.45 MB/s, so USB 1.1 speed; about 7 s of black as the kernel starts; the splash; Total Replay's menu about 105 s after power-on. Linux's own part (kernel start to Total Replay, 31 s) was the smaller one. So mach_kernel's size is most of the boot time. With Debian's default `MODULES=most` the initramfs was 24.4 MB of it. overlay/etc/initramfs-tools/modules now lists only the drivers for the root partition on a USB stick, plus a USB keyboard for the rescue shell (conf.d/applereplay-modules sets `MODULES=list`); everything else loads from the root filesystem after the switch, as before. That gave a 7.0 MB initramfs and a 12.8 MB mach_kernel. On the Apple TV the same day (a second video, same stick): boot.efi's logo for about 31 s instead of 67 (12.8 MB at about 0.42 MB/s), Total Replay's menu about 66 s after power-on instead of 105; Linux reported 22.0 s to the login (8.3 s kernel, against 10.4 s with the big initramfs), no failed units, and TEST_BOX=1 tests/run passed (60 fps median, lowest 59, 40% idle, 67 of 233 MB in use). A reboot right after (filmed too) was no faster: the logo again about 31 s, Total Replay about 60 s after the logo appeared in both videos, 22.6 s to the login; the firmware reads mach_kernel the same way every time, and a first boot from a freshly written stick had no measurable extra cost this time. The reboot itself took about 13 s from the emulator stopping to the firmware starting over (the shutdown splash, then a few seconds of no signal). The firmware's read is still about half the boot, so a still smaller mach_kernel (xz compression, or a kernel with less built in) is where more time would come from (see Next). Compression, measured on the box the same evening (each version of the same 18.2 MB initramfs unpacked five times from /dev/shm with the kiosk stopped, since the box has one core): zstd at Debian's level 9, 7.0 MB, 0.40 s; zstd -19, 6.2 MB, 0.48 s; xz -9e, 5.6 MB, 1.88 s. zstd unpacks at nearly the same speed whatever level packed it, so level 19 saves about 1.9 s of the firmware's read for 0.08 s of CPU; xz would save about 3.3 s of reading but spend 1.5 s more unpacking, and the kernel's own unpacker is slower than the xz tool, so it comes out no better and probably worse. conf.d/applereplay-compress sets `COMPRESSLEVEL=19`: a 6.2 MB initramfs and a 12.0 MB mach_kernel. Level 19 uses an 8 MB window; 6.1's lib/decompress_unzstd.c accepts up to 128 MB (one comment there still says 8 MB), and the kernel unpacked it in QEMU from a USB stick. On the Apple TV (2026-11-18, timed at 10 frames a second from the videos of both builds, same stick): boot.efi's logo for 29.9 s instead of 31.4, so 1.5 s less of the 1.9 s expected; the kernel's part unchanged (9.1 s, within the 8.3-9.0 s seen before); 22.9 s to the login; TEST_BOX=1 tests/run passed (60 fps median). Then (smaller-mach-kernel branch) zz-applereplay-trim also drops what a plain partition on a USB stick never needs: device-mapper (dmsetup, libdevmapper, dm-mod and its udev rules; 0.23 MB after compression), the PS/2 mouse driver initramfs-tools adds (0.06 MB) and Plymouth's DRM renderer with libdrm (0.05 MB): initramfs 5.8 MB, mach_kernel 11.7 MB, about 0.8 s less. On the Apple TV (2026-11-18, timed the same way): boot.efi's logo 29.1 s instead of 29.9, the 0.8 s expected; 22.9 s to the login; TEST_BOX=1 tests/run passed (60 fps median, lowest 59, 45% idle). dm_mod still loads, from the root filesystem after the switch (udev asks for it there), which costs nothing at boot.efi's end. The 'Lessons' item about `MODULES=dep` is a different case: that one guessed modules from the machine doing the build. The biggest file left is libcrypto (4.5 MB, which kmod needs). tests/image.sh checks the size (under 10 MB) and the drivers.
- boot.efi is Apple's (from Apple TV update 2Z694-6013-013.dmg). Dummy.kext is from DistroHopper39B/DummyKext.
- Same author's ATV1sm bypasses the EFI signature check to boot any EFI OS (possible future GRUB route).
- Kernel options: Debian dropped i386 kernels after bookworm, so the newest packaged one is bookworm-security `linux-image-686-pae` (6.1.192-2 as of 2026-11-16). A self-built mainline LTS kernel is possible later.
- **Kernel pinned to 6.1.190 from 2026-11-16 until 6.1.192-2 the same day** (history; how to pin again): hooks/customize.sh installed `linux-image-6.1.0-54-686-pae` by name, not `linux-image-686-pae`, because Debian's 6.1.192-1 crashes in ext4 and freezes the box. Six ext4 commits were backported to 6.1.192 from mainline, including two folio conversions pulled in as dependencies. They check `__filemap_get_folio()` with `IS_ERR()` only, as is right since 6.4, but in 6.1 it returns NULL whenever a block group's buddy or bitmap page isn't cached. So `ext4_mb_load_buddy_gfp()` reads through NULL, and the oops leaves the jbd2 transaction held: every writer (systemd, journald, linapple) then hangs until a power cycle. On this 233 MB box it hit twice: once during an initramfs rebuild, and once 6 minutes after boot on a plain `mktemp -d`. tests/box.sh reproduces it (files written, `drop_caches`, files deleted), and tests/known-bad-kernels keeps 6.1.192 out of the image and off the box. It isn't specific to this box: Debian bug #1154101 (filed 2026-11-15 by others, severity critical, many duplicates merged) has it on amd64, arm64, Xen, KVM and Hyper-V, crashing anywhere from 25 s to hours after boot. The same commits had already crashed 6.1.167-rc1 in March 2026 and were dropped from that release, then came back in 6.1.192. Debian's fix (salsa merge request 2168, "ext4: fix NULL folio dereference in mballoc") was merged into its bookworm-security branch on 2026-11-16; its test build was amd64 only, so nothing has been tried on the box yet. Our write-up is docs/upstream/linux-6.1.192-ext4-null-folio.md. A daily GitHub workflow (.github/workflows/kernel-pin.yml, running .github/kernel-pin-check.sh) watches for the way out: while KERNEL_PACKAGE in hooks/customize.sh is a fixed version, it reads Debian's i386 package lists (bookworm-security and bookworm), and when `linux-image-686-pae` is newer than the pin and not in tests/known-bad-kernels it opens the issue "A Debian kernel to unpin to is out" (GitHub emails the owner) and the run fails; it closes the issue once there's nothing to do. It says nothing about whether the new kernel works: that is the box test's job. Unpinned 2026-11-16: Debian closed #1154101 with 6.1.192-2, whose only change over 6.1.192-1 is that fix; on the box it passed TEST_BOX=1 tests/run, the reproducer included, and hooks/customize.sh installs `linux-image-686-pae` again. To pin again if a kernel goes bad: set KERNEL_PACKAGE to the last good version's package (the daily workflow then watches for the way out) and list the bad version in tests/known-bad-kernels.

## Lessons from the first attempt
An earlier stick (not built from this repo) never worked; every problem came from how the image was put together, not from the hardware:
1. **linapple was copied in as a bare binary** linking libSDL3, libSDL3_image, libzip and libcurl, none of them installed. build.sh now builds linapple in the image and fails on unresolved libraries.
2. **SDL kmsdrm can't work on this GPU:** it needs GBM+EGL, and the G72's Mesa driver (nv30) is barely maintained. Don't pursue it.
3. **Disk options:** `total-replay.hdv` is a 32 MB hard disk image: use `--hd1`, not `--d1` (floppy). The config flag is `--config`, not `--conf`.
4. **A read-only root that never got an fstab** means no logs, no DHCP leases, no random seed, and likely a systemd-logind crash loop. The overlay ships a real fstab.
5. **Missing drivers:** an initramfs built with `MODULES=dep` inside QEMU had no NIC, usbhid or sound drivers. Install the real kernel package in the image.
6. "Gave up waiting for suspend/resume device" costs about 35s at boot: `RESUME=none` (overlay/etc/initramfs-tools/conf.d/resume).
7. No RTC time ("System time before build time"): systemd-timesyncd is enabled.

## Pipeline (all rootless)
1. `./build.sh` (~2.5 min in RAM, ~5 min on disk) -> `out/rootfs.tar` + `out/boot/{vmlinuz,initrd}`. mmdebstrap unshare, working under `$TMPDIR`: build.sh sets it to /dev/shm when that's a tmpfs with 4 GB free and TMPDIR isn't already set (measured on an 8-core PC with a SATA SSD: 309 s on disk, 147-156 s in RAM, peak 1.8 GB there; dpkg syncs every file it unpacks). An interrupted build can leave a `mmdebstrap.*` directory there holding RAM until it's removed; project files go in via sync-in/upload hooks; `hooks/customize.sh` runs inside the chroot (overlay/, kernel, user `apple`, SSH keys, linapple build with patches/, Total Replay, services, tools/fps). Fails if linapple has unresolved libraries.
2. `./mkimage.sh` -> `out/mach_kernel` (atv-linux-loader) and `out/totalreplay.img` + `out/totalreplay.bmap`.

Write: unmount any auto-mounted partitions, then `sudo bmaptool copy out/totalreplay.img /dev/sdX` (the only step needing root), then `sudo sgdisk -e /dev/sdX` to move the backup GPT to the end of the stick. The bmap lists only blocks that hold data, and bmaptool writes nothing else. Images from before 2026-11-15 left the gap between the partition table and partition 1 (sectors 34-2047) as a hole, so it wasn't written, and a reused stick kept what it had there: one that had held an Ubuntu 26.04 installer still showed as "Ubuntu 26.04 amd64" (an ISO 9660 header at 32 KiB) after a correct write, until `sudo wipefs --all --types iso9660` removed it. mkimage.sh now writes that gap as real zeros, so the bmap covers the whole first MiB (tests/image.sh checks it). The rest of a stick past the image doesn't matter, and `sgdisk -e` rewrites its last sectors (the backup GPT). Small changes can be made on the box instead: kernel flags via `sudo mount /boot/atv`.
- Shut the box down before taking its stick out. With its root disk gone, the box keeps running whatever is already in memory but can't start anything new, and it can no longer be shut down cleanly. A fresh login was the only way to send a poweroff, so the only way out was to pull the power. That loses nothing once the stick has been rewritten anyway, but with the stick still unwritten it is an unclean shutdown of its filesystems. If SSH fails this way while ping works, check first that the box still has its stick.

  - **No nouveau.** Apple's firmware leaves a 1280x720 framebuffer (efifb) with the HDMI transmitter set up correctly. As soon as nouveau sets any mode (even 1080p), the TV shows black as purple, white as mint, blue as violet: the transmitter sends YCbCr and the TV reads it as RGB (black = Y16/Cb128/Cr128 shown as R128 G16 B128). Confirmed with tools/av-test and a video of the boot (correct until nouveau loads). So: `modprobe.blacklist=nouveau`, X uses fbdev (overlay/etc/X11/xorg.conf.d/20-fbdev.conf, no shadow framebuffer), no mode changes at all, linapple windowed at `Screen factor = 1.75` (980x672). Not 1.875 (1050x720, the full height): the TV this was tuned on overscans 720p by roughly 3-5% (bottom text line cut in half) with no setting to turn it off, so 24 black lines are left above and below. Still 60 fps (4 source rows -> 7).
  - The picture is fitted to the screen at startup: xsession asks /usr/local/lib/totalreplay/screen-factor, which reads the framebuffer's size (/sys/class/graphics/fb0/virtual_size) and prints the largest factor, in steps of 1/8, that leaves 6.5% of the height and of the width free (1.75 on 1280x720, as before; 2.625 on 1920x1080; 1.125 on 720x480; never below 1), and writes it into linapple's config copy. Steps of 1/8 because the changed-rows drawing needs whole blocks: at k/8, at most 8 Apple II rows become a whole number of screen rows. A TV that shows the whole picture can have more: a number in /etc/totalreplay/screen-factor replaces the computed one (1.875 fills 720 lines); restart the kiosk to apply. The journal has a `screen-factor` line per start ("screen 1280,720, factor 1.75") and the script's complaint about a bad override. Tested on the box at 1280x720 only, computed and overridden; other sizes only through tests/screen-factor.sh.
  - linapple's messages reached the journal only when it exited (its stdout is a pipe, so fully buffered); xsession runs it under `stdbuf -oL`, so "Screen size is 980x672" appears at startup, which tests/box.sh reads.

- Performance: emulation itself is <5% of the CPU; the cost is moving pixels. linapple has no frame skip (one emulated frame + one draw per loop), so speed = fps/60. On any box from the image: `sudo fps [-s] [seconds]` (tools/fps, installed as /usr/local/bin/fps) prints frames per second, the median and lowest whole second (a brief dip shows as a low lowest with a normal median; a box that is slow throughout has a low median; `-s` lists every second) and CPU use, using a uprobe on draw_frame_window through tracefs (no perf needed). Frame counts drop briefly while Total Replay loads from disk; that isn't slowness. For profiling, install linux-perf on the box (`perf record -a`, `perf report --sort comm,dso,symbol`). Steps at 2x (under nouveau, before the efifb switch):
  - Upstream: ~15 fps. Per-pixel 64-bit `__divdi3` in VideoStretch, then ~5 copies of a 3.4 MB frame (stretch, memcpy into the SDL texture, SDL software blit, XShmPutImage, nouveau EXA upload into a freshly allocated and zeroed buffer).
  - patches/linapple-stretch-speedup.patch (division-free stepping, exact-2x fast path, repeated rows memcpy'd; output verified byte-identical to upstream): 25.6 fps.
  - nouveau's `NoAccel` (shadow framebuffer; no per-frame buffer allocation): 31 fps.
  - patches/linapple-sdl2-window-surface.patch part 1 (with SDL's software renderer, draw straight into the window surface; no texture, no renderer): 53 fps.
  - Same patch part 2 (only rescale and send the band of rows that changed since the last frame; full repaint once a second): **60 fps, ~45% CPU idle**.
  - Then on efifb: the changed-rows band is widened to whole blocks that scale exactly (8 source rows -> 15 screen rows at 1.875x, 4 -> 7 at 1.75x), so it works at any scale with output identical to a full redraw: **60 fps, ~47% CPU idle**.
  - Worst case: with fbdev's default shadow framebuffer, scenes where much of the screen changes (attract-mode demos) ran at 52-54 fps, Xorg 18-25% CPU copying the shadow. `ShadowFB false` (XShmPutImage writes straight into the write-combined framebuffer): 59-60 fps over the same two minutes of attract mode, Xorg 1-6%. Further ideas if needed: narrow the dirty band to columns too, an exact fast path for the 4->7 vertical step.
  - Still open (found 2026-11-11 by tests/box.sh): full-screen transitions in the attract mode (e.g. Space Kadet's title screen drawn in over the whole screen, every row changing every frame) hold 56-57 fps with ~28% CPU idle and Xorg ~13%. Spare CPU on average but missed frames suggests some frames overrun 16.7 ms and linapple's pacing then loses a frame. Look at FramePacer and at per-frame times (a uprobe on return of draw_frame_window, or timestamps in the trace). Also unexplained: one `sudo fps 20` during a test run averaged 53.2 fps, 136 frames short, which is more than a 56-57 fps scene can lose in 20 s; so something slower exists (a disk load, or a heavier scene). Seven minutes of per-second counts right after were all 59-61. First dip caught per second (2026-11-11, 30 s): `60 59 60 51 50 48 48 62 59 60`, the rest 59-60; four seconds at 48-51 fps (43 frames lost), mean 58.5, median 60. So dips are short and deeper than 56-57; the 53.2 reading would take about three of these in 20 s, or one longer one. When tests/box.sh shows a low "lowest", look at out/test/fps.txt for its shape.
  - `init_on_alloc=0` (mkimage.sh flags) helped less than first thought (nouveau's EXA path asked for zeroed pages explicitly). Harmless; kept.
- Sound: HDMI audio works through applereplay-hdmi-audio.service; stereo confirmed by ear with tools/sound-test (a voice says "Front left"/"Front right" per channel). Cause: the SiI1390 HDA codec never reports presence (pin sense 0, no ELD), and kernel 6.1's patch_hdmi only binds a pin to its PCM with a valid ELD. Unbound, a stream takes the no-pin path (hdmi_pcm_open_no_pin / prepare with pin_idx < 0), which skips the S/PDIF control assign and the channel setup: DIGI_CONVERT_1 stays 0 (digital out off, silence) and CVT_CHAN_COUNT stays 0 (mono, left channel only). The IEC958 mixer switches can't help (spdif->nid is never assigned). The `inv_jack_detect` hint isn't enough either (ELD still invalid). The service watches /proc/asound/card0/pcm3p/sub0/status and, each time a stream opens, sets DIGI_CONVERT_1=0x01 and CVT_CHAN_COUNT=1 with hda-verb (alsa-tools; root, the hwdep needs CAP_SYS_RAWIO). The codec doesn't implement ASP slot mapping (reads back 0). No audio infoframe is sent; TVs play without one. The SiI1390's own I2C isn't on the SMBus (only 0x48 and 0x69 are there); it hangs off the GPU's I2C.

## Security
What the box is meant to withstand is in SECURITY.md (a home network; physical access is full access). How it's built:
- SSH: keys only, no root login (overlay/etc/ssh/sshd_config.d/totalreplay.conf); user apple has no password and passwordless sudo, so the key in out/ssh is root. build.sh makes each builder their own key; out/ is never committed, and a built image must not be shared (it holds the host keys).
- Firewall: overlay/etc/nftables.conf, loaded by nftables.service. In: SSH, mDNS (udp 5353), ping/ICMPv6, DHCP replies; everything else dropped; out: anything. Without it the box listened on sshd 22, avahi 5353 plus two random UDP ports, and dhclient 68. Gotcha: the image has no /etc/protocols (no netbase), so nft can't resolve `ipv6-icmp`; write `icmpv6`. To try rules on a live box without locking yourself out: `sudo systemd-run --on-active=120 /usr/sbin/nft flush ruleset` first, then load them, and stop the timer once a new SSH login works.
- The two root services are confined with systemd options (`systemd-analyze security`: 9.6 "unsafe" before, 1.7 after). applereplay-fb-wc keeps only CAP_SYS_ADMIN (to read /proc/iomem and write /proc/mtrr), applereplay-hdmi-audio only CAP_SYS_RAWIO plus the ALSA devices (hda-verb's ioctl). Not usable: PrivateDevices on hdmi-audio (hides /dev/snd and drops CAP_SYS_RAWIO), ProtectKernelTunables on fb-wc (untested; it makes parts of /proc read-only).
- linapple runs as apple and is built without its FTP client (see linapple facts). X runs with -nolisten tcp.
- Updates: apt's timers are masked, so the box never updates itself (a kiosk shouldn't run apt mid-game). Security fixes arrive by rebuilding and rewriting the stick, or `sudo apt update && sudo apt upgrade` over SSH. `env/vuln-check` lists the vulnerabilities in out/rootfs.tar that Debian has fixed (debsecan against Debian's security tracker; `--all` adds the unfixed ones, about 2,500 lines, mostly kernel entries counted against linux-libc-dev). The Debian 6.1 kernel gets security updates until bookworm LTS ends (2028).
- Watching for new vulnerabilities, on GitHub: .github/workflows/vulnerabilities.yml runs every Monday (and by hand from the Actions tab). GitHub can't build the image (the assets aren't in the repository), so it checks docs/image-packages.status, the package list of the last recorded build (480 packages; only the fields debsecan reads, which gives the same result as the full dpkg status file), with .github/vuln-report.sh. When Debian has fixed something the list lacks, it opens an issue titled "Debian has security fixes the recorded image lacks" (or updates the open one) and the run fails; when nothing is left it closes the issue. Keep the list current: after a rebuild you flash or publish, `env/vuln-check --record` and commit the file. Limits: it speaks for the recorded build, not for anyone's stick; it covers Debian packages only, not linapple, cctools-port or Total Replay; GitHub switches scheduled workflows off after 60 days without a commit, and a click in the Actions tab turns them back on. Dependabot (.github/dependabot.yml) covers the two things it understands, the atv-linux-loader submodule and the workflow's actions, with monthly update pull requests; it has no alerts for this repository because there is no package manifest it can read. While the kernel is held back (see Kernel pinned to 6.1.190), linux-libc-dev, the kernel headers, stays at Debian's newest version, so the kernel's own missing fixes aren't counted; the report says so in a note whenever the image's kernel and linux-libc-dev differ. Kernel fixes show up under `linux-libc-dev`: debsecan matches packages to the tracker by source package, and that is the one built from source `linux`, while the kernel image comes from `linux-signed-i386`, which the tracker doesn't list. A running box can't take those from `apt upgrade` (it boots the kernel in mach_kernel), so the report says a kernel fix needs a new image. The report lists at most ten identifiers per package (a kernel release can fix a thousand). First real result, 2026-11-15: 1,015 kernel fixes, because Debian 12 had moved from 6.1.190-1 (the recorded build) to 6.1.192-1 since that morning; the full dpkg status file gave the identical count, so the trimmed list loses nothing. First run on GitHub: 2026-11-16, started by the push of the 6.1.192 package list; it succeeded with nothing to fix (the check step passed and the failing step was skipped) and opened no issue. The report goes to the run's summary page, not its log. The report script is also tested locally: tests/static.sh, by hand against a list with an old libssl3 (35 fixes), and against Debian's live tracker through env/run.
- Pinned inputs: linapple (build.sh), atv-linux-loader (submodule), cctools-port (env/build-cctools.sh) are commits, not branches; assets.sha256 has the hashes of the files each builder fetches (a mismatch warns, since a newer Total Replay is legitimate). Debian packages are whatever the archive has on the build day, checked by apt against env/keyring.
- tools/av-test runs as root on the box: it keeps its files in a `mktemp -d` directory, not fixed names in /tmp.

- A smaller mach_kernel, for a faster boot. The firmware reads it from the stick at about 0.42 MB/s, so each MB is about 2.4 s on boot.efi's logo, and that read is still about half the boot (see Where boot time goes). Today's 12.0 MB is the kernel (5.8 MB) plus the initramfs (6.2 MB with zstd -19; 18.2 MB unpacked). Compression is settled (zstd -19; xz measured and not worth it, see Where boot time goes). Ideas, roughly in order of effort:
  - Considered and rejected (2026-11-18): removing libcrypto from the initramfs. It is the biggest file (4.5 MB unpacked, 1.68 MB of the compressed initramfs, about 4 s of the firmware's read), there because Debian's kmod and libkmod link OpenSSL; libkmod is also inside udev's udevadm, which loads the USB drivers, so a different modprobe wouldn't remove it. They import 19 OpenSSL functions, all for decoding module signatures (modinfo), which loading modules never calls, and both are linked with BIND_NOW. So a stub libcrypto.so.3 defining those 19 symbols (version OPENSSL_3.0.0) would work, but it would be our own code impersonating Debian's library in the one place where a mistake stops the box booting, and it would need checking after every kmod update: the same kind of trade as a self-built kernel, for 4 s of a 66 s boot. Taking udev out of the initramfs is riskier still.
  - Strip the initramfs further (device-mapper, the PS/2 mouse driver and Plymouth's DRM renderer are gone, see Where boot time goes): list what's in it (`zstd -dc out/boot/initrd | cpio -it`) and drop what a USB-stick root never uses. What's left is needed, except Plymouth (plymouthd, its plugins, libpng, libm: about 1.3 MB unpacked, perhaps 1-2 s): without it in the initramfs the splash would start only after the switch to the root filesystem, a few seconds of black later. Decided 2026-11-18 to keep it: the splash from the start is worth more than that time.
  - The kernel itself: Debian's 686-pae has much built in that this box never uses. A self-built kernel with only the Apple TV's hardware could be a fraction of 5.8 MB, but it goes against "keep Debian's kernel" (Hardware and image facts) and loses Debian's security updates, so it's the last resort.
  - Check each step with a phone video from power-on (time on boot.efi's logo) and tests/image.sh's size check, which could then be tightened.
- Surviving a power pull: a read-only root, and maybe a small writable area. The Apple TV can't switch itself off, so every session ends with the plug pulled: after a clean shutdown ("safe to turn off") when it goes as planned, but in a kiosk sooner or later in the middle of a game. The root is a normal read-write ext4; its journal keeps the filesystem consistent but not a file being written at that moment, and cheap sticks are known to lose data when power drops mid-write. What writes while the box runs: Total Replay's disk image (it saves preferences and high scores inside total-replay.hdv; a damaged copy means Total Replay doesn't start), the journal, the DHCP lease, the clock and random-seed files, Plymouth's boot-time estimate (/var/lib/plymouth), and anything done over SSH (apt upgrade, env/devroot install). No damage seen so far, but the power has never been pulled on a running game on purpose. Options (discussed 2026-11-18, not decided):
  1. Leave it: simplest, fine so far; the risk is a damaged game disk after an unlucky pull, and the fix is rewriting the stick (which also loses the saves).
  2. Read-only root with writes going to RAM (an overlay on tmpfs; the box has the room, about 67 of 233 MB in use): every boot starts clean and nothing can be damaged, but high scores, preferences and logs are lost at each power-off, and updates over SSH need a way to make the root writable again. How to set it up with initramfs-tools (rather than a systemd initramfs) is still to be checked.
  3. Read-only root plus a small writable partition in the stick's unused space (see Image layout), for what should survive: the game disk or just its saves, and a little system state. The system can't be damaged; a pull can only hurt that partition, which could be checked at boot and reset from a pristine copy of the game disk kept on the read-only root. The most work, and it overlaps growing the root partition (both want the unused space) and Total Replay updates (keeping saves when the .hdv is replaced), so design them together.
     - Updates over SSH under option 3: one command (e.g. the planned applereplay-update) runs `mount -o remount,rw /`, the update (apt upgrade, env/devroot install, overlay files), then reboots, which brings the root back read-only. A reboot rather than `remount,ro`: after an upgrade, running programs still hold the old, deleted files, and Linux refuses to make a filesystem read-only while files on it are open for writing; the reboot also starts the new programs. apt's own state stays on the root (written only in that window); kernel updates still need a new mach_kernel from the build host, as today. What writes during normal running moves off the root, to the writable partition (to keep it) or to RAM: the DHCP lease, the clock and random-seed files, Plymouth's boot-time estimate, the journal if it's to be kept. Total Replay's updates and saves touch only the writable partition, so updating it needs no maintenance window at all.
     - Saves could survive rewriting the stick (today a rewrite loses them, see Updating a box that is already running): if the image's partition table includes the writable partition but leaves its contents a hole, bmaptool doesn't write it (it writes only blocks that hold data), so a rewrite replaces the system and leaves the saves. The box formats that partition only when it finds it blank (its first boot); that check has to be exactly right, since a mistake erases the saves. The partition must fit the smallest supported stick, so a few hundred MB right after the root, within 8 GB. Untested.
  - How option 3 would meet updates to the software stack (2026-11-18): Debian, slightly more work: every update needs the remount/update/reboot window, and an update can bring a new program that writes to the root during normal running, which then fails; tests/box.sh's "no failed services" catches it, but each one needs moving off the root. Kernel updates are unchanged (mach_kernel). Rebuilding and rewriting the stick, today's main update path, gets better if the saves survive a rewrite (above). linapple, about neutral: env/devroot install needs the window (its install step can remount); what linapple writes while running has to live on the writable partition or in RAM: the game disk (/var/games/apple2/total-replay.hdv, owned by apple), and its config, which xsession copies from /etc/totalreplay/linapple.conf into ~/.config/linapple/ at every start and linapple writes back on exit (Save State On Exit is 0, but a save state made by hand goes in its Save State Directory, also under home). A linapple update can't touch the saves. Total Replay, clearly better: the .hdv lives on the writable partition, so an updater replaces it with no window and can keep the previous one for rolling back. Carrying high scores and preferences into a new release is the same problem either way; option 3 only keeps it away from the system. One point to settle: a reset of a damaged game disk must not bring back an older release after an update, so reset from the last good copy kept on the writable partition rather than from a copy on the root. Tests to adjust: the ext4 reproducer in tests/box.sh writes on the root (it would have to use the writable partition), and the box test could check that nothing writes to the root.
  - Reliability, not security: whoever has the SSH key is root (passwordless sudo) and can remount the root writable and change it for good, and physical access is full access either way (SECURITY.md); the game disk stays writable by apple as today. So none of the options is a security measure, and SECURITY.md shouldn't count one as such. Two details so it doesn't make things worse: keep systemd's random seed on persistent storage (the writable partition, not RAM), so early-boot randomness doesn't rely on the kernel alone; and keep the journal persistent too if login records should survive a power-off (in RAM they would not, which also counts against option 2).
  - First, find out whether it's a real problem: measure what gets written during an hour of play (/proc/diskstats, or watching which files change), then pull the power mid-game a few times and check that the box boots, that `e2fsck -n` on the root is clean, and that Total Replay starts with its saves. Worst case is rewriting the stick. If that's harmless, option 3 stays an idea; if the game disk gets damaged, that is the reason and the detail for it. The owner's choice between keeping saves (3) and losing them at each power-off (2) decides the direction.
- Then: Apple Remote (hid-appleir), verify.sh, or a lighter emulator.
- Growing the root partition to fill the stick: only if a need for space appears. mkimage.sh makes a fixed 6 GB root so the image fits an 8 GB stick and writes quickly; a first-boot step (growpart plus resize2fs, as Raspberry Pi OS does) could enlarge it to the whole stick. No use for it so far: about 1.3 GB of the 6 GB is used, Apple II disk images are tiny (Total Replay is 32 MB), and journald limits itself. Against it: a step that rewrites the partition table and resizes the live filesystem, on a box that is always switched off by pulling the plug, and sticks that then differ from each other. The unused space may be better kept for the writable partition in Surviving a power pull (option 3).
- Total Replay updates. Releases (github.com/a2-4am/4cade, one `Total.Replay.hdv` asset each, 33,553,920 bytes): 5.0 2023-05, 5.0.1 2023-11, 5.1 2024-02, 5.2 2024-09, 6.0 and 6.0.1 2026-06, 6.1 2026-08 (built and tested with 6.1). So 1-3 a year, irregular (a 21-month gap before 6.0), with commits in between. Today an update means replacing assets/total-replay.hdv and rebuilding. Options: an on-box `totalreplay-update` that fetches the latest release (GitHub's releases/latest API), checks size and that it boots, keeps the old image to roll back to, then restarts the kiosk; or a check at boot that only reports a new version. Caveat: Total Replay saves preferences and high scores inside the .hdv, so replacing it loses them; find out whether they can be carried over (they live in a few files on the ProDOS volume).
- Publishing: the repo is public at github.com/arguingbananas/applereplay (branch main, first pushed 2026-11-11, with GitHub's private vulnerability reporting turned on, which SECURITY.md relies on). Before any push: tests/static.sh, which looks for home paths, private IPs, personal email addresses, private keys and host names (see Tests); those belong in CLAUDE.local.md or out/. The .gitignore keeps out:
  - out/: build output, including the private SSH key (out/ssh) and the box's SSH host keys (out/hostkeys).
  - env/root, logs and tarballs: the build environment, gigabytes, regenerated by env/bootstrap.sh.
  - assets/: Apple's boot.efi (proprietary), Dummy.kext, total-replay.hdv (free from Total Replay's project, but it contains commercial games). The README says where to get each.
  - CLAUDE.local.md: notes about one particular setup.
  - src/atv-linux-loader is a git submodule (clone with `--recurse-submodules`, or `git submodule update --init`).

## Upstream contributions (to send back, with thanks)
Fixes worth offering to the projects this box depends on. Patches live in patches/.
- **linapple** (github.com/linappleii/linapple):
  - patches/linapple-i386-snapshot-align.patch: the save-state `static_assert(snapshot_size_fixed_body == 132344)` fails on i386 (132340) because `uint64_t` members are only 4-byte aligned there; `alignas(8)` on two members fixes it. Upstream only builds on 64-bit today.
  - patches/linapple-stretch-speedup.patch: VideoStretch did a 64-bit division per pixel (`__divdi3` on 32-bit, the top cost on a 1 GHz CPU); replaced with exact stepping, plus an exact-2x fast path and memcpy of repeated rows. Byte-identical output (tested against upstream on 25 MB of cases).
  - patches/linapple-joystick-hat.patch: a host controller's d-pad (hat 0) drives the Apple II joystick at full travel, overriding the analog stick while pressed. Adds `sdl_compat_get_joystick_hat` to the sdl1, sdl2 and sdl3 back ends; built and run for sdl2, compiled for sdl1, not compiled for sdl3 (Debian 12 has none), so check that one before sending.
  - patches/linapple-sdl2-window-surface.patch: when SDL hands out its software renderer, draw into the window surface directly and update only the rows that changed (at any scale, in blocks that scale exactly). 25.6 -> 60 fps on the Apple TV. Upstream may want it behind a check or option; it changes nothing for accelerated renderers.
  - Report: `--fullscreen` uses `SDL_WINDOW_FULLSCREEN`, a real mode change to the nearest mode (640x480 here). An option for `SDL_WINDOW_FULLSCREEN_DESKTOP` plus the existing aspect-fit scaling would suit TVs better.
  - Report: SDL2 frontend crashes inside Mesa's nouveau_dri.so on GeForce 7 (nv40) unless `SDL_RENDER_DRIVER=software SDL_FRAMEBUFFER_ACCELERATION=0`; worth a note in the docs (the bug itself is Mesa's).
- **Mesa** (nouveau nv40): segfault at `nouveau_pushbuf_kick` from SDL2's GL texture framebuffer on a G72. Only worth filing with a reproducer.
- **xf86-video-nouveau**: with EXA on nv4x, each XShmPutImage allocates and zeroes a new buffer (kernel_init_pages ~15% of CPU). Maybe report.
- **atv-linux-loader** (DistroHopper39B): a note for its docs: on HDMI, nouveau makes the picture purple (YCbCr read as RGB); blacklisting nouveau and using efifb (plus a write-combining MTRR) gives correct colours.
- **ALSA HDA (kernel, patch_hdmi)**: the Apple TV's SiI1390 (0x10951390) never reports presence or an ELD, so HDMI audio stays silent and mono until DIGI_CONVERT_1 and CVT_CHAN_COUNT are set by hand. A quirk for this codec (e.g. static_pcm_mapping, or treating the pin as always present) would make it work out of the box. Report with a codec#1 dump and the register values.
- **Debian / stable 6.1.y** (kernel, ext4): 6.1.192 dereferences NULL in `ext4_mb_load_buddy_gfp()`; the backported folio conversions assume mainline's ERR_PTR return from `__filemap_get_folio()`. Write-up with oops, cause, reproducer and suggested fix: docs/upstream/linux-6.1.192-ext4-null-folio.md. Nothing to send: others reported it the day before ours was ready (Debian #1154101, forwarded to a linux-ext4 patch series), and Debian's fix is merged. Added to #1154101 on 2026-11-16: that i686 is affected too, and the four-line reproducer. Debian closed it with 6.1.192-2, which passes the reproducer on the box; a one-line "confirmed on i686" there would close the loop.
- **nouveau** (kernel): on the Apple TV, any nouveau modeset leaves the SiI1390 sending YCbCr the TV reads as RGB. Worth a report with dmesg and the DCB.

## linapple facts (upstream github.com/linappleii/linapple)
- Pinned to commit 0b22441 (2026-11-05). master uses CMake with `-DFRONTEND=sdl3|sdl2|sdl1|tui|headless`. Debian 12 has no SDL3, so use `-DFRONTEND=sdl2`. Build deps: g++ cmake libzip-dev zlib1g-dev imagemagick libsdl2-dev (sdl1 also needs libsdl1.2-dev libsdl-image1.2-dev), plus libcurl4-openssl-dev unless `-DENABLE_FTP=OFF`.
- It has an FTP client (libcurl) for fetching disk images from an archive site, on by default. Blank `FTP Server` settings don't turn it off (the code falls back to the built-in address); the build option `-DENABLE_FTP=OFF` does, and both hooks/customize.sh and env/devroot use it (they must match, or the devroot binary stops being identical to the image's).
- CLI: `--hd1 <file>` (inserts hard disk in slot 7), `-a/--autoboot`, `-c/--config`, `-f/--fullscreen`.

## Notes
- QEMU can test systemd/network/service logic (boot the kernel+initrd with `-kernel/-initrd`), but cannot reproduce boot.efi or the G72/nouveau/KMS behavior.
- Original Apple TV firmware has no native PXE/NetBoot; a local boot drive is required.
- /root on the stick is mode 0700; reading it from another machine needs sudo.
- Alpine/OpenRC was considered and rejected; stay on Debian.
- Working with whoever is at the TV: only they can judge colours, overscan and sound. tools/av-test (colour screens, plus tones per output) and tools/sound-test (spoken left/right) make those checks quick; a phone video helps (its stereo mics can't separate left from right, though).
